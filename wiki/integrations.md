# Cross-application contracts: Current, Beacon, Ledger

This document is the contract the three applications implement. Each side links here from its own docs. Field names
are exact; anything not listed is free to evolve.

The applications were renamed (Umbrella Flow → Current, Umbrella Monitoring → Beacon, Inventory DB → Ledger, SPA →
Keystone); the identifiers on the wire keep their old spelling (`flow_` and `umb_` tokens, `x-inventory-*` headers,
`inventory-db:` references, `/api/integrations/inventory-db/*`, `/api/integrations/flow/scope`, the integration kind
`flow`, the `network-flow` connector and the `umbrella-flow` source of events and proposals).

## 1. API tokens (all three apps)

Every app accepts machine access with a bearer token in addition to sessions:

- Header `Authorization: Bearer <token>`. Ledger keeps accepting `xc-token` as well.
- Token format: `<prefix>_<random 32 bytes base64url>`; prefixes `flow_` (Current), `umb_` (Beacon). Ledger keeps its
  existing tokens.
- A token belongs to a **service account** (or a user) and carries that account's role; permission checks are the same
  as for sessions. Tokens never need CSRF headers.
- Only a keyed hash (HMAC-SHA256 with a key in OpenBao) is stored; the plaintext is shown once at creation. Tokens
  have a name, optional expiry, `last_used_at`, and can be revoked. Creation, use from a new address and revocation are
  audited.
- UI: Settings → API tokens (Current), Settings → Service accounts (Beacon).

## 2. Current ↔ Ledger

### 2.1 Ledger → Current: traffic for DCIM objects

Ledger's integration kind `flow` stores `flowUrl` and a Current API token (role with `integrations.inventory:read`)
in OpenBao, and calls Current server-side (the browser never sees the token).

`GET {flowUrl}/api/integrations/inventory-db/status?object_type=<type>&ids=1,2,3[&window=24h]`

- `object_type`: `dcim.device`, `dcim.interface`, `circuits.circuit`.
- Response:

```json
{
  "window": "24h",
  "results": {
    "12": {
      "in_bps": 7200000000, "out_bps": 1300000000,
      "speed_bps": 10000000000, "utilization_in": 0.72, "utilization_out": 0.13,
      "p95_month_bps": 6900000000, "commit_bps": 5000000000, "over_commit": true,
      "sparkline": {"t": ["2026-10-12T09:00:00Z", "…"], "in": [1.0, 2.0], "out": [0.5, 0.7]},
      "flow_url": "https://current.corp/visualize?q=…",
      "last_seen": "2026-10-12T10:46:00Z"
    }
  }
}
```

- Current rates are the last 5 minutes; the sparkline has 48 points over `window`.
- Devices aggregate all their interfaces (`ExporterRef = inventory-db:dcim.device:<id>`); interfaces are matched by
  device + name; circuits by `InIfCircuit` / `OutIfCircuit` = circuit cid, `p95_month_bps` and `commit_bps` only for
  circuits and interfaces with a circuit. Unknown ids are omitted. `utilization_*` are `null` when the speed is unknown.

`GET {flowUrl}/api/integrations/inventory-db/prefix-addresses?prefix=10.0.0.0/24[&vrf=<name>][&window=24h]`

```json
{"prefix": "10.0.0.0/24", "results": [{"address": "10.0.0.7", "bytes": 123456, "flows": 42,
  "last_seen": "2026-10-12T10:40:00Z", "in_ipam": false}]}
```

Addresses seen as source or destination inside the prefix, up to 1024, ordered by bytes; `in_ipam` is computed by Current
from its Ledger snapshot.

### 2.2 Ledger → Current: change notifications

On every committed DCIM / IPAM / circuits change (`netboxEvents`), Ledger POSTs (debounced to at most one request
per 5 s per integration, coalescing events) to:

`POST {flowUrl}/api/integrations/inventory-db/hook`

```json
{"integration_id": "int_…", "events": [{"event": "object.updated", "object_type": "dcim.interface", "id": 12}],
 "sent_at": "2026-10-12T10:46:00Z"}
```

Signed like Ledger's Beacon webhook: `x-inventory-timestamp: <unix seconds>`,
`x-inventory-signature: v1=<hex HMAC-SHA256(secret, "<timestamp>.<raw body>")>` (two comma-separated signatures during
rotation); requests older than 5 minutes are rejected; 401 for any failure. The shared secret is generated by
Ledger when the integration is created (shown once) and stored by Current in OpenBao. Current answers 202 and schedules an early
inventory sync (debounced).

### 2.3 Current → Ledger

- Reads: the NetBox-compatible API with an `xc-token` (read-only user) — already implemented.
- "Create in Ledger" from Current's Unknown lists: `POST /api/v1/ipam/ip-addresses/` (`{address: "10.0.0.7/32",
  status: "active", description: "Discovered by Current", tags: []}`) with a separate optional token of an
  editor user (`inventory_write_token` in OpenBao). Without that token the action is hidden.
- Ledger auto-creates the custom field `snmp_index` (integer, object type `dcim.interface`) when a `flow`
  integration is created, if it does not exist.

## 3. Current ↔ Beacon

### 3.1 Events (done)

Current's detector posts to Beacon's `network-flow` connector (see Beacon's `app/docs/current.md`).

The device manager ([devices.md](devices.md)) posts to the same connector through the same sender. Current has no alert
table or notification channel of its own for devices. A managed network device that fails two polls in a row raises
one event:

| Field | Value |
|---|---|
| `signal` | `use.device.down` |
| `method`, `severity` | `USE`, `critical` |
| `ci` | the device name (from Ledger when the device is bound) |
| `source_ref` | `inventory-db:dcim.device:<id>` for a device bound to Ledger, absent for a standalone one |
| `ip` | the device address |
| `id` | `flow-` + 20 hex characters, one per down episode, so the next outage opens a new incident |
| `status` | `firing` while the device is down; `resolved` when a poll succeeds again, or the device is disabled or deleted |
| `labels` | `source: umbrella-flow`, `device_id`, `platform`, `host`, `site`, `role`, `error` (last poll error) |
| `links.flow` | `<public URL>/devices/<id>` |

The event has the same shape as the detector's events, so the connector treats it the same way: it finds the CI by
`source_ref` (else by name and IP) and keeps the method and severity as sent.

### 3.2 Current → Beacon: visibility scopes

Current holds a Beacon service-account token (Beacon permission `integrations.flow:read`) in OpenBao.

`GET {umbrellaUrl}/api/integrations/flow/scope?username=<login>`

```json
{"username": "ivanov", "known": true, "mode": "all" | "teams" | "selected",
 "cis": [{"id": "ci_…", "name": "app-01", "source_refs": ["inventory-db:dcim.device:100"], "ips": ["10.0.0.5"]}],
 "services": [{"id": "svc_…", "name": "Billing"}]}
```

`mode: "all"` → `cis` and `services` are empty and mean "everything". Users are matched by login (case-insensitive;
both apps get their users from Keystone, so the logins are the same). Unknown user → `{"known": false}`. Current caches per user for 60 s and,
for a user whose Current role has `scope:umbrella`, restricts every ClickHouse query with
`(SrcCI IN refs OR DstCI IN refs OR SrcAddr IN ips OR DstAddr IN ips)`.

### 3.3 Current → Beacon: dependency proposals

Current discovers steady CI ↔ CI traffic (both ends resolved to Ledger refs or Beacon CI IPs; ≥ N flows on ≥ M
of the last 7 days; server port detected) and posts proposals daily and on demand:

`POST {umbrellaUrl}/api/cmdb/proposals` (permission `cmdb:propose`)

```json
{"source": "umbrella-flow", "generated_at": "2026-10-12T10:00:00Z",
 "proposals": [{
   "key": "flow:inventory-db:dcim.device:100->inventory-db:dcim.device:200:tcp/5432",
   "from": {"source_ref": "inventory-db:dcim.device:100", "name": "app-01", "ip": "10.0.0.5"},
   "to":   {"source_ref": "inventory-db:dcim.device:200", "name": "db-01", "ip": "10.0.1.9"},
   "type": "depends_on",
   "evidence": {"protocol": "tcp", "port": 5432, "app": "postgres", "bytes_7d": 123456789, "flows_7d": 4200,
                "days_seen": 7, "first_seen": "…", "last_seen": "…", "flow_url": "https://current.corp/visualize?q=…"}
 }]}
```

→ `{"accepted": n, "updated": n, "ignored": n}`. Beacon resolves both ends to CIs, derives the implied service
dependency (service of `from` depends on service of `to`), stores proposals keyed by `key` (upsert, evidence
refreshed), and shows them on the CMDB map page ("Proposed dependencies": accept → creates the service dependency;
reject → hidden for that key unless evidence grows 10×). Proposals not refreshed for 14 days expire.

### 3.4 Beacon → Current: links (done)

`/go/incident?ci=&ip=&ref=&from=&to=` (see `docs/api.md`).

### 3.5 Grafana

`deploy/grafana/flow-ci-traffic.json` (identical in Current's and Beacon's `deploy/grafana`): dashboard "CI traffic" on the
ClickHouse datasource (`grafana-clickhouse-datasource`, uid `flow-clickhouse`) with variables `ci`, `ci_id`, `ip`, `ref`
— Beacon's incident context link fills them. A CI matches as an end of the traffic (`SrcCI` / `DstCI`, `SrcAddr` /
`DstAddr`) and, for routers and switches, as the exporter (`ExporterRef`, `ExporterAddress`).
